# Phases 150–151 — a simpler front door, and staff who can sign themselves back in

Plan, 2026-11-07. The owner accepted all five decisions below the same day.
Nothing here is built yet. Claude writes, Codex reviews, staging first.

## Why

1. The start screen shows everything twice (English, then Indonesian). Staff
   only need to know one thing: "I'm staff, how do I get back in?"
2. A staff phone that gets signed out has no way back except a new invite link
   from the owner. If the owner is busy or away, that person can't log work.
3. There is no logo on the start screen, so it doesn't feel like the same app
   as the loading screen just before it.

Staff phones are Android. Likely reasons a staff phone ends up signed out
(not yet measured):

- the WhatsApp link opens in the phone's default browser (often Xiaomi's,
  Oppo's or Samsung's own), and later they open Miamus from Chrome, which has
  no session;
- phone "cleaner" apps or low storage wipe the browser's data;
- the app treats a bad connection as signed out (PR #2 fixes this one).

A way to sign back in without the owner covers all three.

## Phase 150 — the start screen (no database change)

**One language at a time, picked from the phone.**

- A phone set to Indonesian sees the screen in Bahasa Indonesia; any other
  phone sees English. Read from `navigator.languages` ("id", "id-ID" and the
  old "in" count as Indonesian).
- A small `SegmentedControl` in the top corner ("EN | ID") switches it. The
  choice is remembered on that phone (localStorage, try/catch).
- Why not English only: Indonesia is in the "low" band of the EF English
  Proficiency Index (2025: 471, 80th of 123; Jakarta 523, "moderate"). Most
  target owners will read English, but older owners and households outside
  Jakarta may not, and signed-out staff land here too.
- A new owner's first language prompt (/onboarding) starts on the language
  the start screen was showing. They still confirm it.

**The Miamus logo** (`MiamusMark`, already used on the loading screen) above
"Welcome to Miamus".

**Two clear ways in**, replacing the yellow "Masuk dengan PIN?" warning:

- Main button: **Continue with Google / Lanjutkan dengan Google** (owners).
- Second button: **Saya staf**, in Indonesian on both language versions so
  staff recognise it at once (owner, 2026-11-07). Until Phase 151 ships, it opens a
  short screen: "Minta link undangan baru ke admin rumah lewat WhatsApp."
  After Phase 151, it opens the house-code sign-in.

**Same rule on the other public pages**: /join/owner (co-owner invite) follows
the phone's language with the same switch. /privacy and /privasi stay as they
are (one page per language, already linked to each other).

**Files**: `src/app/page.tsx`, `src/app/join/owner/page.tsx`, a small
`usePublicLocale()` hook, `onboarding/page.tsx` (preselect).

**Privacy**: nothing new collected. The remembered language is stored on the
phone only. The policy already covers settings kept on the phone, so I'll
check its wording, but expect no change.

## Phase 151 — staff sign in with a house code and PIN (migration 115)

### How it works for staff

1. Start screen → **Saya staf**.
2. Type the **kode rumah** (house code), e.g. `K7M-2QX`.
3. Tap their name (the same list the staff screen shows today).
4. Type their 4-digit PIN → they're in, on the staff screen.

Invite links keep working exactly as now. The code is the way back in, not a
replacement.

### How it works for owners (Access tab)

- **Kode rumah / House code** card: shows the code, a "Send on WhatsApp"
  button, and **Change code**. Changing the code does not sign anyone out; it
  only stops the old code working for new sign-ins.
- **Linked phones / HP staf yang terhubung**: every staff phone linked to the
  household, with when it was last used and a **Remove** button. Today owners
  can't see these at all. With a code that anyone in the house can be told,
  owners need to see and remove phones.
- A push notification when someone's PIN gets locked (below).

### Why not "household name + PIN"

- Household names are guessable ("Rumah Budi") and not unique.
- A PIN is only 4 digits (10,000 options), and today nothing limits wrong
  guesses. That has been fine so far, because only a phone already linked
  through an invite can try a PIN. A sign-in open to anyone who knows a name
  would let a stranger try every PIN and see the household's photos,
  schedules and stock.

### Security design

- **The code**: 6 characters from an alphabet without look-alikes (no 0/O,
  1/I/L), shown as `XXX-XXX`. About 887 million combinations. Generated by
  the database, unique, changeable by an admin only.
- **Wrong-PIN limit**: 5 wrong PINs for one staff member → that person is
  locked for 15 minutes, and the owners get a push ("PIN Sari terkunci
  setelah 5 percobaan salah"). The same limit is added to `verify_staff_pin`,
  closing today's gap on phones that are already linked.
- **Wrong-code limit**: 10 wrong codes from one phone session per hour → that
  phone waits an hour.
- **Only anonymous sessions** can use a house code (handoff conflict 6). A
  phone signed in with Google gets a message instead, so an admin's account
  can never be turned into a staff device.
- **Linking happens only after the right PIN**: one function checks code,
  name and PIN, and links the phone (`device_sessions`) in the same
  statement. A right code alone shows the names and nothing else.
- **Database rules (AGENTS.md)**: every new `SECURITY DEFINER` function
  revokes `EXECUTE` from `public, anon` and grants only what's needed.
  Code-sign-in functions → `authenticated` (staff phones are anonymous but
  authenticated). Admin functions (show, change code; list, remove phones)
  check the caller is in `household_members` (or use
  `caller_admin_household()` if that has merged by then — it is not on this
  branch yet), never `get_user_household_ids()`, which staff phones pass.

### Database (migration `115_staff_house_code.sql`, additive only)

- `households.staff_join_code` (text, unique, nullable; filled for every
  existing household by the migration).
- `staff_sign_in_attempts` (staff id or null, phone session id, household,
  time, success). Used for the limits, deleted after 30 days by its own
  daily pg_cron job, set up the same way as 113's request clean-up.
- `staff_profiles.pin_locked_until` (timestamptz, nullable).
- Functions: `house_code_roster(code)`, `sign_in_with_house_code(code,
  staff_id, pin)`, `my_house_code()`, `rotate_house_code()`,
  `list_linked_phones()`, `remove_linked_phone(id)`; `verify_staff_pin`
  replaced in place with the limit.

### Privacy policy (both languages) — before this ships

- New: failed and successful staff sign-in attempts (who, when, which phone
  session), kept 30 days, used only for security.
- New: owners can see which staff phones are linked and when each was last
  used.
- `src/config/legal.ts`: retention line if it lists retention periods.

### Testing

- Migration: on a throwaway local database first, then staging. Each needs
  your OK, as always.
- Cases: right code + right PIN links the phone; wrong PIN ×5 locks and
  pushes; a locked PIN fails even when right; wrong codes ×10 blocks; a
  Google session is refused; a removed phone is signed out on its next
  request; after a code change the old code fails and linked phones keep
  working; a logged-out caller (anon) can't call anything.
- Browser: the whole staff flow at 360 px on an Android-sized screen, and
  the owner Access cards in both languages.
