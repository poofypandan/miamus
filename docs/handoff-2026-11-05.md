## 2. Privacy policy

**Status:** written 2026-11-05, **not merged**. It sits uncommitted on the
owner's Mac, branch `staging`:

- `src/config/legal.ts` — operator **Poofy Labs**, contact
  **support@poofylabs.dev**, `policyVersion` `2026-11-05`, data region
  "Tokyo, Japan".
- `src/components/legal/privacy-policy.tsx` — the text, English and Bahasa
  Indonesia side by side.
- `src/app/privacy/page.tsx` (English, for admins) and
  `src/app/privasi/page.tsx` (Bahasa Indonesia, for staff). Both public.
- Notices: the sign-in screen ("By continuing, you agree to Miamus's Privacy
  Policy"), household setup (the admin confirms the policy and agrees to tell
  their staff what is recorded), and the staff name screen ("Miamus mencatat
  tugas, foto, dan cuti kamu untuk rumah ini." + link to `/privasi`).

It is written against Indonesia's Personal Data Protection Law (UU PDP, Law
No. 27 of 2022). If the two languages differ, Bahasa Indonesia prevails. It is
not legal advice.

### What it says about personal data

| Data | What the policy says | Who can see it | How long it is kept |
| --- | --- | --- | --- |
| Staff names | Entered by the household admin | Admins, and staff phones in the same household (name picker) | While the household uses Miamus. Archived staff keep their name on past work; the admin or the person can ask for removal |
| Staff PINs | 4 digits, stored only as a one-way hash; nobody can read them back | Nobody — the column is not readable | Until changed; cleared when the person is archived |
| Photos: chore and routine proof, before/after | Taken in the app, kept in private storage | The household | Deleted automatically after 30 days (nightly `prune-task-photos` job) |
| Photos: pet photos, pet document scans, stock-check photos | Same | The household | While the household uses Miamus |
| Leave | Dates and status | The household (see note below) | While the household uses Miamus |
| Staff phone sign-ins | A random ID per staff phone and when it was last used; push-notification details if turned on | Only that phone's own record | While the household uses Miamus — no automatic cleanup exists |
| Admin accounts | Name, email and profile picture from Google sign-in | Co-admins see each other's email | While the account is used |
| Kept only on the phone | Sign-in session, selected staff name, photos waiting to upload offline, app-lock settings. Face ID / fingerprint data never leaves the phone | Nobody else | — |

**Note on "who can see it":** the policy says staff see "the tasks, schedules
and information they need for their work". At database level, any staff phone
in a household can read all of that household's tasks, staff names, leave
records and pet records, because row-level security grants by household, not
by person. **OPEN — owner decides:** tighten the database rules, or reword the
policy.

### Deletion and erasure requests

The policy promises:

- deletion within 30 days of a request, for a whole household or one person,
  unless the law requires keeping it;
- a copy in a common, machine-readable format on request;
- correction, and withdrawal of consent;
- the right to complain to Indonesia's data protection authority;
- notice of a data breach to affected people and the authority within
  3 × 24 hours (UU PDP Article 46).

Requests go to support@poofylabs.dev. **No deletion or export tooling exists
yet. OPEN — owner decides** how this is done (at minimum, a documented manual
script). The policy also says copies in providers' backups are cleared on their
normal schedule; on the current free Supabase plan there are no backups.

### Outside services that handle data

| Service | What it handles | Named in the policy? |
| --- | --- | --- |
| Supabase | Database, sign-in, photo storage, nightly photo cleanup. Production is in Tokyo (AWS ap-northeast-1) | Yes |
| Vercel | Hosts the app. Photos pass through `/api/photo` when shown, but aren't stored there | Yes |
| Google | Admin sign-in | Yes |
| Apple, Google and Mozilla push services | Deliver notifications to phones | Yes |
| Anthropic (Claude) | The app itself sends no data to Anthropic (no Claude API in the app). But Claude sessions with database access — the Supabase connector, `DATABASE_URL` in `.env.local`, PR #1's settings — can read production personal data into the conversation | **No. OPEN — owner decides:** keep Claude sessions on staging/test data, or name Anthropic in the policy |
| OpenAI (Codex) | Reviews code on GitHub; sees no user data unless it is committed | No (code only) |
| GitHub | Hosts the code | No (code only) |

### Rules the code must follow because of the policy

- The only public contact is support@poofylabs.dev, set in
  `src/config/legal.ts`. No personal email or phone number in user-facing text,
  config or emails.
- Changing what is collected, where it is stored, which services touch it, or
  how long it is kept → update `privacy-policy.tsx` (both languages) and
  `legal.ts` in the same PR. Coming up: house code + PIN sign-in, a wider
  offline save queue, a possible region move (`dataRegion`).
- Don't change the 30-day photo window (`task_photo_retention_cutoff()`,
  migration 102) without updating the policy.
- PINs stay hashed and unreadable (migrations 095, 096, 107). Never expose the
  `pin` column.
- `/privacy` and `/privasi` stay public (the middleware only guards
  `/dashboard` and `/onboarding`).
- Staff-facing text in Bahasa Indonesia, admin-facing text in English
  (`CLAUDE.md`).
- Archiving keeps the person's name on past work and revokes their PIN. The
  policy's retention section describes exactly that; keep it that way.

### How migrations are numbered and applied

- Files: `supabase/migrations/NNN_name.sql`, numbered in order. 000–108 are on
  `main`; 109–110 are in PR #1; 111 is uncommitted on the Mac. **The next new
  file is 112.**
- The database's own history uses the number for 000–108 (applied with the
  CLI) and a timestamp for changes applied through the Supabase connector,
  named `phase_<n>_<slug>`.
- Rule (decided 2026-11-05): every database change is a numbered file in the
  same PR, applied to **staging first, then production**. Never edit a file that
  has been applied; add a new one. Never introduce breaking migrations; keep
  historical foreign keys nullable (`CLAUDE.md`).
